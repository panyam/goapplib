# goapplib

A Go web-app framework (server-rendered pages, mixins, htmx, templates through templar) with the TS packages `tsappkit` and `tsappkit-solid`. See SUMMARY.md for an overview, the docs site (https://panyam.github.io/goapplib/, built from `docsite/`) for how to use it, and CAPABILITIES.md for the stack-facing API and version. Bump CAPABILITIES.md whenever the API changes.

## Commands

- `make setup` sets up the git hooks. `make test` runs all the tests, including `make wasm-test` (the wasmhost tests as wasm under Node, which needs `node` on PATH).
- `make exercise-wasmhost` is mission #33's exercise: it builds `exercise/wasmhost` to wasm and drives it in headless Chromium (playwright-core; locally it uses `~/.cache/ms-playwright`). `make exercise-wasmhost-gen` regenerates its proto code with buf and local plugins.
- `make exercise-islands` is mission #60's exercise: a Go page (`exercise/islands`) whose islands have different load strategies, driven in headless Chromium at 1200 and 400 px. Its `below` island is a real `SolidIsland`, so the page is built by `exercise/islands/build.mjs` (esbuild with `esbuild-plugin-solid`) rather than the esbuild command line; the script points tsappkit-solid's `@panyam/tsappkit` and `solid-js` imports at one copy, and the `one-copy` check fails if a second one gets bundled. Checks still waiting on a ticket sit in `pending` in `exercise/islands/run.mjs`; a pending check that passes fails the run (`XPASS`), so the PR that fixes it must take it off the list. Each run saves screenshots to `exercise/islands/dist/screenshots/`, and CI keeps them as the `exercise-islands-screenshots` artifact.
- `make exercise-worker-state` is mission #74's exercise: a toy stateful service (`exercise/workerstate`, plain JSON over `http.Handler`, no proto) as wasm in a Web Worker. Its first load ingests 32 MB of state through a 256 MB peak in a throwaway worker (`oneShotFetch`), restores it in the serving worker from the cache, then runs three 2 s long jobs on a separate `startLane` lane; the serving worker is a lane too, with a restore-only warm and a 96 MB `maxMemoryBytes` that a 100 MB churn request trips (one with a quick query to the serving worker beside it, one read as a stream, one aborted); after a reload the page only reads the state back. Checks waiting on a ticket sit in `pending` in `exercise/workerstate/run.mjs`, with XPASS as in the islands exercise, and CI keeps its screenshots as `exercise-worker-state-screenshots`.
- `make exercise-docsite` is mission #91's exercise: it builds the s3gen docsite in `docsite/` (its own Go module), runs its Go tests (templates parse, nav wired, internal links resolve), then loads every page and runs every live demo in headless Chromium (`docsite/run.mjs`). A demo is `docsite/demos/<name>/`, embedded with `{{ demo "<name>" }}` and run in its own iframe; it calls `ready()` or `failed()` from `demos/_lib/frame.ts`. A demo with a `wasm/` directory gets its Go built to wasm with the wasmhost worker and `wasm_exec.js` beside it (`docsite/build.mjs`); `docsite/go.mod` requires goapplib with `replace ../`, so the wasmhost guide's demos reuse the exercises' services. A demo with a `page/` directory is an island page: a Go `main` (`docsite/internal/islanddemo`) renders its `index.html` at build time from a `page.Spec` and the bundle's metafile, since Pages can't run a server. The Go API reference (`docsite/content/reference/api.md`) is generated from the source by `docsite/apiref.go`, and a test fails the build if an exported name is missing, so new API needs no doc edit there. Guide code that's a whole app lives in `docsite/examples/<name>/` and is included with `includeFileText`, so it's compiled and tested rather than retyped (the old guides' snippets didn't compile). Checks for what the mission still needs sit in `pending` in `run.mjs`, with XPASS as in the other exercises. `.github/workflows/docs.yml` runs it on every PR and deploys `docsite/dist` to https://panyam.github.io/goapplib/ from `main`. `docsite/README.md` has the page-adding steps.
- Images for a PR description go on the orphan `pr-assets` branch under the PR number (`pr-assets:63/…`) and are linked by commit (`https://github.com/panyam/goapplib/raw/<sha>/63/x.png`), so `main` carries no binaries.
- When a capability lands, tag a release (`v0.x.y`). Consumers (thambura, agni, lilbattle) bump to the tag. A release is a "Release vX.Y.Z" commit on main when the versions need setting, then an annotated tag and a GitHub Release whose body is the notes; there's no CHANGELOG file. Push the tag before `gh release create`: given a tag that doesn't exist yet, gh makes a lightweight one at `main`'s head (v0.6.9's tag is lightweight for that reason). The repo is Apache-2.0 since v0.6.9, and each npm package carries its own copy of `LICENSE`.
- Version bumps are patches (0.6.x) by default, even for new API or a small break with no outside callers. Ask before a minor.
- **One version for everything.** goapplib, `@panyam/tsappkit` and `@panyam/tsappkit-solid` share the version under `## Version` in CAPABILITIES.md (lock-step since v0.6.0), so `v0.6.0` means the same thing in `go.mod` and `package.json`. A PR that bumps one bumps all three, and the release tag is that version. `scripts/check-versions.sh` checks it in CI, and `publish.yml` runs it with the tag before publishing anything.
- A `v*` tag also publishes the TS packages (`.github/workflows/publish.yml`, through `scripts/npm-publish.sh`): each package whose `package.json` version isn't on npm yet is built, tested and published. npm accepting the publish counts as success; the script waits up to 2 minutes for `npm view` to show it and otherwise leaves a warning on the run. So the first PR after a release that changes either package bumps all three versions to the next one. CI's `DRY_RUN=1 scripts/npm-publish.sh` fails when a package's contents differ from the published version with the same number. Auth is npm trusted publishing, so there's no token; a failed run can be retried from the Actions tab (`workflow_dispatch`). Each package names `panyam/goapplib` and `publish.yml` as its trusted publisher, set with `npx npm@latest trust github <package> --repo panyam/goapplib --file publish.yml --allow-publish` (needs a recent npm, which `npx npm@latest` gets, plus a login and an OTP); `npm trust list <package>` shows it. Both packages have it since v0.6.0, so a tag publishes with no manual step; without it the job fails with `E404 Not Found - PUT` and needs `npm publish --access public --otp=<code>` by hand.

## Gotchas

- **TS packages and pnpm 12.** Each package (`tsappkit`, `tsappkit-solid`) needs `allowBuilds: {esbuild: true}` in its own `pnpm-workspace.yaml`, or `pnpm install --frozen-lockfile` fails on esbuild's build script. A consumer installing a release that's only hours old gets a `minimumReleaseAgeExclude` entry added to its workspace file; that's expected.
- **0.x peer ranges.** `^0.0.5` means 0.0.5 only, and `^0.1.0` means 0.1.x only, which is why tsappkit-solid's peer on tsappkit is `>=0.0.5 <1.0.0` (since 0.0.4). Keep it a plain range, or every tsappkit minor needs a solid release.
- **npm lag.** A new version can take a while to show in `npm view` and the package's `latest`. Usually it's minutes and the per-version URL (`https://registry.npmjs.org/@panyam/tsappkit/0.3.0`) answers first, but v0.6.8's tsappkit-solid said "being processed" and wasn't at either for 29 minutes. Don't re-run a publish that npm accepted: it would refuse the same version again.
- **Spec golden file.** `page/testdata/spec.json` is Go's exact `Spec.JSON()` output, `\u003c` escapes included. Regenerate it from Go's output rather than retyping it, since editors and some tools turn `\u003c` back into `<`.
- **tsappkit tests run in jsdom.** `BasePage` calls `window.matchMedia`, which jsdom lacks, so a test that constructs a page stubs it (see `tsappkit/src/page/IslandPage.test.ts`).
- **wasmhost exports never block.** Every `<ns>.*` export copies its arguments and returns a Promise, doing the work on a goroutine (`promise()` in `wasmhost/js.go`). Work run inside the `js.FuncOf` callback hangs as soon as a handler waits on JS, and it hangs rather than failing, which is why `wasm-test` has `-timeout 60s`.
- **Streaming out of a busy worker works; reaching into one doesn't.** A Go handler's `Flush` reaches the page mid-loop (a synchronous JS call), but nothing posted to the worker (a second request, a cancel) is seen until the handler yields or returns. A lane's abort terminates the worker for that reason, and `oneShotFetch` and lanes keep a worker until its streamed body ends (`untilBodyEnds`).
- **Wasm tests under Node.** Await each JS Promise as soon as it's created. Node ends the process on a rejection with no handler yet, so building several rejected promises and awaiting them later crashes the test binary.
- **Worker and client ship together.** A page from one tsappkit version must load that version's `wasmhost/worker.js`. The v0.2.0 worker treats an unknown request kind as `unmount`, so a newer page's `addFiles` against a cached old worker unmounts the mount.
- **Screenshot the viewport, never the full page, in island tests.** A full-page screenshot resizes the viewport to the whole document, which puts every slot in view and sets off `visible` islands.
- **Debugging islands.** Add `?islands` to a page's URL for the overlay (each slot labelled with its island, load and state). In a test, `page.CheckIslands(assets.Names(), specs...)` catches a spec naming an island the registry doesn't have.
- **Solid's `render` appends to its container** rather than replacing what's there, which is why `SolidIsland.activate` clears its element first (#39). And two copies of solid-js in one bundle don't break a click test, so check for them in the metafile (the exercise's `one-copy` check) rather than in the browser.
- **Pick the wasmhost piece by the problem.** Rebuildable state across a reload: `wasmhost.Cache` (`BrowserCache`), keyed by `CacheKey` of the inputs. A job with a big transient peak: `oneShotFetch`, leaving its result in the cache. Quick requests behind long ones, or aborting a job that never yields: `startLane` per kind of request. A long-lived worker creeping up: `maxMemoryBytes` on its lane, with a restore-only `warm` (a warm that can ingest pulls the peak back in). `exercise/workerstate/` uses all of them. Measure before choosing: `oneShotFetch` only pays when the peak dwarfs the live state (agni's Jetson rebuilds 285 to 320 MB of model per worker, so its 100 MB parse peak didn't justify it), and each lane holds its own copy of the state (agni went from about 455 MB to 800 to 889 MB with two lanes).
- **Late islands start on their own.** An island with a non-eager `load` mounts after the page's `LifecycleController` has finished, so it gets its own; nothing orders its `activate` after the page's. Don't defer an island something else needs at startup. A `lazy` registry entry always mounts late, eager or not.
- **`go build` fails in a worktree of this clone** with `error obtaining VCS status: exit status 128`, since the clone is a bare repo with worktrees. Pass `-buildvcs=false` (the docsite's Makefile sets `GOFLAGS` to it). It isn't a compile error.
- **goapplib's layout reads fields a page has to bring.** `BasePage.html` reads `.Header.AppName`, `.Header.IsLoggedIn`, `.Header.Username` and `.NavigationItems` (each `{Href, Label, Active}`) from every page, and goapplib defines no types for them, so a page without them fails with `can't evaluate field`. A page's template overrides `BodySection` through `namespace` and `extend` (see `docsite/examples/hello`), since defining it again fails with `multiple definition of template`.
- **Template actions in an HTML comment are live.** Go templates parse `<!-- {{ define "X" }} -->` as a real definition, which once made every `BorderLayout` render its comment's example toolbar. Put examples in templar's `{{#/* ... */#}}` comment, as `BasePage.html` does. `templates/page/Islands.html` is parsed by plain `html/template`, so it can't use that syntax.
- **One PR closing two issues needs "Closes" before each.** "Closes #111 and #95" closed only #111 (PR #112). Write "Closes #111, closes #95", and check `gh pr view N --json closingIssuesReferences` after opening.
- **A PR with merge conflicts runs no `pull_request` workflows**, while CodeQL still reports green. If `test` and `exercise-wasmhost` are missing from a PR's checks, check `mergeable` first.
